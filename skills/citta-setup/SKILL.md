# Citta device setup

Set up the requested device and prove that a task executes on a different device. Citta's private repository is `priyankark/citta`. Find an existing checkout first; otherwise clone it with the user's established GitHub credentials. Use the same reviewed commit as the other devices. If no release is tagged, identify the commit being qualified; do not call it a production release.

Read the checkout's `docs/setup.md` for commands, `docs/capabilities.md` when adding a worker, and `docs/acceptance.md` for the rollout evidence. These files describe the actual installed version; prefer them to assumptions about CLI flags. Read `docs/operations.md` for repair, rotation, upgrades, or rollback.

## Establish existing state

Inspect OS/architecture, Citta binary/version, current config/service, Tailscale connection and Serve routes, and intended harness/capabilities. Discover device IDs and URLs from existing configuration where available. Ask only for missing device access or capability choices needed to finish. Continue local installation and validation while waiting for remote access.

Keep the existing identity, secrets, peers, and unrelated harness/network settings. `citta init` is for new installations and refuses to overwrite. A startup lock failure usually means a daemon is already running. Do not remove locks or reset a database to bypass it.

Explain access during onboarding using the intended work, not a blanket list of grants. Read `docs/setup.md` → “Choose what this device should do”: coding needs the receiving harness/tools and working files; connected apps need that device's account/tool connection; desktop input/capture may need macOS Accessibility and Screen Recording; Apple events may need the specific app's Automation grant. Verify existing access before asking the user to change anything. Give the exact device, executable/app and next action for a missing grant. SSH, public Funnel and Full Disk Access are not general prerequisites.

## Install and pair

Before compiling, check the receiving device’s compiler version against this checkout’s qualified toolchain and inspect free disk space for the build, installation and backup. Prefer a verified artifact for the same OS/architecture and reviewed commit when local resources are constrained. Follow `docs/operations.md` → “Build and artifact preflight”; preserve the global toolchain and unrelated caches.

For a downloaded artifact, verify that the receiving OS permits it to execute before running setup or tests. If macOS requests per-app approval, explain which verified file needs approval on that device and use the system's approval flow within the owner's authorization. Report an OS denial as an installation blocker rather than claiming application test coverage.

For macOS upgrades, compare the installed/candidate signing identity and designated requirement before replacement; the same path does not guarantee retained desktop grants. Follow `docs/operations.md` → “macOS signing identity and desktop access”. Stage the candidate if required OS approval cannot be completed. Verify grants and actual input/capture from the restarted service's worker, not an interactive shell. Recover only a compatible prior binary after idle/schema checks and a current backup; preserve current database/config/history. Do not restore stale state, edit TCC records or use an unrelated signing identity to recover desktop access.

1. For a new installation, install the verified artifact or build/install the reviewed checkout with `cargo install --path . --locked` using its qualified toolchain, then run the **installed binary** with `citta setup`. It discovers Tailscale, preserves or initializes device identity, configures private Serve, installs a persistent user service, merges Codex MCP, and installs the setup/delegation skills. CLI commands default to `~/.config/citta/config.toml`; use `--config <absolute-path>` for another installation. `setup --dry-run` reports prerequisites without writing or starting anything.
2. For an existing device on an older build, build a separate candidate and use `scripts/upgrade_device.py` after stopping the idle service; follow `docs/operations.md`. Then run its installed `citta setup`. Preserve identity, credentials, history, policy and existing profiles. Do not overwrite a running binary, reinitialize, or silently downgrade. Setup is repeatable configuration, not a binary self-updater.
3. Setup detects the local signed-in Codex CLI and configures the `codex` full-tool profile if no agent profile exists. It uses fixed arguments, approval policy `never`, `danger-full-access`, the node’s configured slots and a 24-hour maximum timeout. Bash, filesystem writes, network access, configured MCP tools and installed skills are available. Further delegation is permitted; child tasks require explicit collection/cancellation. Use `--agent-access full` to add this profile to a device that already has another profile; use `--agent-access read-only` only when read-only execution is explicitly requested. It uses a configured model when available; `--model` pins one for a new profile. Existing profiles and paused/allowed-origin policies are preserved. Check `agent_configured`, `profile_grant_pending`, `daemon_reachable` and `mcp_explicitly_disabled` in the output. A missing harness/login is incomplete agent setup: address it locally and rerun. `--no-agent` is only for explicitly pairing-only devices. `--no-service` is for externally managed services; restart those through their owner and rerun setup to finish any pending profile grant.
4. Run `citta doctor` and `citta enrollment`. All devices use the same HTTPS port (default 7332). Discovery and reciprocal pairing are automatic for untagged, unexpired devices on the pinned owner/tailnet; credentials refresh without restarts. Do not ask for pairing codes, copied secrets, emailed keys or SSH as a normal setup prerequisite. Tailscale membership does not install software: each device needs one local installation/setup by its agent or an already available deployment channel. If none exists, finish local work and report the specific missing installation. Do not claim installation succeeded because Tailscale discovered the device.
5. Verify actual tool discovery in a new/reloaded harness session. Existing explicit MCP disablement is retained and reported; do not override it silently. Citta task tools use local stdio without embedded tokens. Other harnesses can wire this same stdio server using their supported config; do not label Codex-specific automatic wiring as universal harness support.

When the owner explicitly requests full access for all existing agents, also migrate the existing agent profiles rather than leaving older restricted aliases active. Preserve their model and harness choices, update the fixed arguments using that harness’s supported full-access mode, remove Citta-specific tool-disable overrides, and update descriptions. Retain a referenced profile name as a compatibility alias when needed. Verify a real shell/file-write/skill/tool task through each affected harness. Ordinary setup without that request preserves existing profiles.

Setup refuses identity changes and conflicting Serve/Funnel routes before replacing an existing live configuration. It backs up changed files under the private config directory and preserves unrelated settings. An existing service pointing at another binary/config must be upgraded in place. Do not reset all Tailscale routes or remove locks to force a retry. Use the lower-level instructions in `docs/setup.md` only for custom deployments or builds predating `setup`.

## Prove the result

Setup passively installs `citta-desktop` with its portable source helpers alongside this skill. For requested macOS desktop work, load that receiving-device skill and follow its usage reference to install the pinned prebuilt addon and compile the two small helpers only when needed. This requires no extra model/provider API or app-hosted computer tool: the worker can use its shell and image-viewing tools. Coding-only setup does not run npm, a compiler, OS prompts or a desktop server. Identify the permission-responsible process, then verify actual marker delivery and capture before app work.

Report paired, agent-configured and task-verified separately. Read setup's `next_steps` and `permissions` guide; its executable path applies to that local device. The `execution_verified: false` and `desktop_verified: false` fields mean that command did not perform worker tests, not that a prior task failed. Mark untested app/desktop access as unverified. For requested desktop use, test from an actual Citta-launched worker, not an interactive terminal: deliver a marker to an owned test window and inspect a captured image. Follow `docs/operations.md` for idle-service restart after OS grants. For an authorized email or other app action, verify the intended receiving-device account before acting and inspect provider evidence afterward; a successful agent exit alone does not prove the action completed.

Require the automatic enrollment report to list the other device as paired with fresh Tailscale identity, then run discovery in both directions. Submit a unique-key `echo` task with `target_node` set to the other device; inspect it on its originating device. Require the expected remote `worker_node`, successful result, and echoed payload. Repeat in the reverse direction. Local echo success alone is insufficient.

Next, discover and use one real capability installed only on the remote device through MCP. Record the tested commit, device IDs/OS, task IDs, and observed result without secrets. Follow `docs/acceptance.md` for interruption, sleep/wake, restart, and capacity checks as part of the requested rollout.

Reusing the same submission key is safe for a transport retry while history is retained. An interrupted task may have performed side effects: inspect before intentional resubmission with a new key. Do not change keys just to make a failed check appear successful.

For resource/session discovery, agent profiles, and the human panel, read `docs/discovery.md`. Declare capability `harness` and `model` metadata only when known; keep model metadata consistent with a pinned runtime configuration. Verify fresh CPU/RAM telemetry, the harness collector status, harness/model fields, and profile kinds through `citta agents`; absent/old telemetry is unknown. Test a requested profile with `spawn-agent` and inspect the durable result. Apply the user’s requested tool access; the full-tool profile inherits installed skills and configured MCP tools. Track any delegated children explicitly because cancellation does not cascade. For owner controls, read `docs/permissions.md`. Verify automatic management pairing as well as task pairing; older peers need the same permissions-enabled build. Use `panel --network` for a private HTTPS browser link from another device. Keep management credentials separate from MCP/task credentials, preserve existing policy, and do not enable allow-all merely to make a test pass. Issue panel links without logging them; they are short-lived owner credentials. An idle observed session is not permission to take it over.

Finish with installed paths, service state, paired device IDs, tested task IDs, and specific outstanding device checks. If remote access is unavailable, state that local setup is verified and cross-device acceptance remains pending; never report enrollment complete from a localhost test.

## Resource-aware runtime delegation

For automatic offloading, deploy the resource-admission build to both origin and receivers. It uses storage version 4; follow the offline backup/upgrade procedure. Install `skills/citta-delegate` from the matching checkout into each originating harness’s skills directory, preserving automatic invocation. Keep the setup and runtime skills separate. Verify Citta MCP tool discovery includes `citta_placement`, `citta_delegate`, and `citta_lookup`; use the documented CLI fallback for an already-running harness that cannot reload tools.

Configure at least one useful agent profile on each intended receiver. Pin its declared model in its fixed harness arguments and grant the selected profile under the existing device policy. Prefer full-tool `codex` for general coding tasks. Do not impose read-only execution or disable Citta tools merely because a task was delegated. Set realistic per-profile `[capabilities.resources]` estimates and `[admission]` memory headroom / CPU cutoff. Use `guard_all = true` when the device should apply admission to legacy jobs too. Do not lower estimates merely to get a test through.

Verify placement reports unknown/stale telemetry and unsupported old peers as ineligible. Exercise an unpinned resource-qualified task when one candidate has insufficient capacity, check that the other device executes it, then retrieve its output on the origin. Use a controlled test policy or fixture, never exhaust a live user's RAM. Verify same-key lookup/retry preserves task identity and a completely busy mesh queues or expires without silently executing unguarded. Record physical-device results separately from local multi-daemon simulations. If a receiving device exposes only echo and has no management channel, finish the runtime/skill work that is possible and report that installation blocker; pairing is not remote installation authority.
